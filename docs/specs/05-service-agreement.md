# Service Agreements

**Module:** 05 — Service Agreements
**Status:** Built (Phase 1)
**Entities:** ServiceAgreement, ServiceAgreementMeter

## Overview

The Service Agreement is the core billing unit of the Utility CIS. It is the contract that says: "Account A receives Commodity B at Premise C, measured by Meter(s) D, billed at Rate Schedule E on Billing Cycle F, starting on date G." Every bill generated by the system originates from a ServiceAgreement.

The ServiceAgreementMeter junction table links one or more physical meters to an agreement. Most residential service has one meter per agreement. Commercial and industrial accounts may have multiple meters contributing to a single billing calculation (e.g., a main meter plus a check meter, or multiple sub-meters that are summed for billing).

**Who uses it:** CSRs starting and stopping service, billing staff confirming rate and cycle assignments, field operations staff confirming which agreements a meter belongs to.

**Why it matters:** The ServiceAgreement is the convergence point of all the system's entities. Without a valid ServiceAgreement, meter reads cannot be billed. The status lifecycle enforces orderly service starts and stops, and the meter assignment uniqueness constraint prevents double-billing.

The PATCH input schema is `.strict()` — passing any field not in the table above returns 422 with a Zod error. Lifecycle fields (`startDate`, `endDate`, `status`) are intentionally rejected: they go through the dedicated `POST /:id/close` endpoint, which cascades onto meter assignments atomically. Fields that cannot be changed after creation under any path: `agreementNumber`, `accountId`, `premiseId`, `commodityId`.

## Business Rules

### Status Transitions

Strict linear progression — no skipping, no INACTIVE state:

```
PENDING → ACTIVE → FINAL → CLOSED
```

Implemented in `packages/shared/src/validators/service-agreement.ts`:

```typescript
export const VALID_STATUS_TRANSITIONS: Record<AgreementStatus, AgreementStatus[]> = {
  PENDING: ["ACTIVE"],
  ACTIVE: ["FINAL"],
  FINAL: ["CLOSED"],
  CLOSED: [],
};
```

Attempting an invalid transition (e.g., `PENDING → FINAL`, `ACTIVE → CLOSED`, or any transition to/from `INACTIVE`) returns a validation error. `CLOSED` is terminal; no further transitions are permitted. The `INACTIVE` status does not exist on ServiceAgreement — agreements stop via `FINAL → CLOSED`.

### Meter Assignment Uniqueness

When creating a ServiceAgreement, the provided meters are validated to ensure none are already active on another agreement for the same commodity. This check runs inside a `$transaction`. If a conflict is detected, the entire agreement creation rolls back with an error naming the conflicting meter.

The check is **belt + suspenders**: a partial GIST exclusion constraint `no_double_assigned_meter` (migration `20260427143900`) on `service_agreement_meter` is the source of truth — it prevents the same physical meter from being on two open assignments concurrently regardless of which code path is doing the write. The application-layer pre-check survives because it produces a friendlier error than the raw `exclusion_violation` from Postgres at COMMIT time.

### Effective-Range Overlap Prevention

A partial GIST exclusion constraint `no_overlapping_active_sa` (migration `20260427143408`) prevents two `PENDING`/`ACTIVE` SAs from overlapping in time on the same `(utility_id, account_id, premise_id, commodity_id)`. The constraint is built on a generated `effective_range tsrange` column derived from `start_date` and `end_date`. Closed/Final SAs are exempt — historical ranges are immutable facts, and a successor SA may validly cover the same window.

A `chk_sa_end_ge_start` CHECK constraint enforces date ordering at the row level.

### Cascade-Close on Lifecycle Transition

The `closeServiceAgreement` helper (in `effective-dating.service.ts`) is the only path to terminal status for an SA. It atomically:
1. Marks the SA `FINAL` or `CLOSED` with the supplied `endDate`.
2. Sets `removed_date = endDate` on every still-open child `service_agreement_meter`.
3. Emits one audit row for the SA + one per cascaded SAM.

The cascade is intentionally **not optional** — the prior code paths (`transferService`, `moveOut`) silently left meter assignments dangling when the parent SA closed. Callers who need different `removed_date` values per meter call `removeMeterFromAgreement` for each one BEFORE the close; the cascade then becomes a no-op on those pre-closed rows (idempotent).

The DB-layer `enforce_sa_lifecycle_invariants` trigger (migration `20260427144400`) is the second line of defense. It rejects:
- `INSERT/UPDATE` setting `status IN (FINAL, CLOSED)` without `end_date`.
- `UPDATE` setting `end_date` while keeping `status` in `PENDING/ACTIVE`. Use the close endpoint, which bundles the two writes.

### Meter-Premise Commodity Match

At creation time, every meter in the `meters` array must:
1. Have a `commodity_id` matching the agreement's `commodity_id`
2. Have a `premise_id` matching the agreement's `premise_id`
3. Have a `commodity_id` that exists in the premise's `commodity_ids` array

All three conditions ensure the meter physically makes sense for the agreement.

### At Least One Meter Required

The `createServiceAgreementSchema` requires `meters` array with `min(1)`. An agreement cannot exist without at least one meter assignment. This ensures every agreement can produce meter reads and billing.

### Effective Dating

`start_date` and `end_date` define the period of service. The rate schedule and billing cycle in effect at billing time are resolved from the agreement's rate/cycle FKs. Rate schedule version history (effective dates on RateSchedule) allows the system to bill at the correct rate for a given period even if the rate changes mid-cycle.

### Read Sequence

`read_sequence` is an integer that places this agreement in order within its billing cycle's meter reading route. Lower numbers are read first. This field supports route optimization for manual meter reading.

### Structural Immutability

The following fields cannot be changed after agreement creation:
- `agreementNumber` — permanent human-readable reference
- `accountId` — agreements belong to one account; to move service, close and re-create
- `premiseId` — agreements are at one location; to move service, close and re-create
- `commodityId` — an agreement is for one commodity; a separate agreement handles each commodity

### Soft Delete / Close

Agreements are never hard-deleted. The terminal state is `CLOSED` with `end_date` populated.

### Filters for List View

The GET list endpoint supports filtering by `accountId` and `premiseId` to support embedded list views within Account Detail and Premise Detail pages.

That message names the date it looked up to, which a generic "nothing to bill" would lose, and that date is what tells a clerk whether they are waiting on a reader or on a cycle.

**Assigning a rate schedule — Overview tab (shipped 2026-10-22).** Until that day this had no UI at all: the panel was read-only and `/rate-schedules/:id` → Agreements was a placeholder, so an agreement created in the app could never be billed without a hand-written API call. The panel now has **Assign schedule** and a per-row **Remove**, both gated on `rate_schedules:EDIT` rather than `agreements:EDIT` — the row joins the two and the API gates it on the schedule side.

`createSAScheduleAssignment` checks only that the agreement and the schedule belong to the caller's tenant. It does **not** check that their commodities match, that the schedule is published, or that two windows for one role overlap. The dialog carries the first two, because both mistakes are silent when made and surface much later inside a billing run:

- **The picker is narrowed to the agreement's commodity**, and drops superseded versions — a replaced version keeps its `publishedAt`, so it would otherwise read as a legitimate choice. With no schedules for that commodity it says so and points at Rate Schedules, rather than showing an empty list.
- **Drafts are not offered.** The picker briefly allowed them with a warning, on the reasoning that "assign now, publish later" was a real workflow. **It is not, and this is worth stating because the distinction is easy to get backwards: publishing is not activation.** `bill-segment.service` picks assignments by the *assignment's* own date window and then refuses any schedule with no `publishedAt` — so the dates decide when a schedule applies, and publishing decides whether it may ever be billed. "Publish now, assign from a future date" therefore covers every case, while a draft assignment is a configuration that looks complete, cannot bill, and says so only when a run fails hours later. The other argument for allowing them — that a freshly seeded tenant has nothing but drafts, so the picker would be empty — was circular: the seed now publishes its schedules.

  An empty picker caused by drafts says so and names the count, since the tariff exists and one click fixes it: *"No published rate schedules for Potable Water — 1 exists as a draft."* That is deliberately different from having no schedules at all, which sends someone to create one.

- **An existing assignment pointing at a draft still shows "Draft — not billable"** on the panel. New ones cannot be made, but rows created before this change exist, and that marker is where someone looks when a run refuses an account.

- **Role** says which part of an unbundled tariff a schedule provides: `primary` for a bundled commodity where one schedule does everything (water, sewer, solid waste), and `delivery` / `supply` / `rider` / `opt_in` where they are separate — which is why one electric agreement in the seed carries `NWE-REDS-1` as `delivery`, `NWE-ESS-1` as `supply` and `NWE-USBC-1` as `rider` at once. It is reference data in `rate_assignment_role` with labels and no descriptions. **Nothing in rating reads it yet:** `loadBase` carries it into the engine's assignment type, and the one selector that would consume it, `source_schedule_role`, throws `"not yet implemented (slice 3)"`. So today the role is documentation plus the key this screen's clash check uses — every overlapping assignment is rated regardless of role, which is why two overlapping ones double-charge.
- **Overlap is still not enforced anywhere** (schema: "Overlap exclusion is deferred to slice 2/3"), but the dialog now *names* it. A schedule the agreement already holds is labelled "already assigned" in the picker — a commodity often has exactly one schedule, so the single option offered is frequently the one already in place, and offering it unmarked invites a duplicate. And choosing a role that an existing assignment still holds on the new effective date raises a warning naming that window. The check is keyed on the **role**, not the schedule: two *different* schedules both `primary` and open-ended is the case that breaks rating, and a schedule-keyed check would miss it. A window that closed before the new one opens is history rather than a clash, since superseding a schedule is exactly "end the old one, start the new". None of this blocks the save — the API permits it and a deliberate overlap may be intended — it just stops the mistake being silent.

Two known limits. **Remove is a delete, not an expiry**, so it loses the record of what applied when; expressing "this schedule ran until March, that one after" needs an editable end date, which this screen does not have yet. And the empty panel now says the agreement cannot be billed until it has a schedule, which is the other half of the diagnosis a `SCHEDULE_NOT_PUBLISHED` or missing-assignment failure needs.

## Migration Notes

### Effective-Dating Constraints (Slice 1, 2026-04-27)

Migrations applied in this slice:

| Migration | Adds |
|---|---|
| `20260427143217_btree_gist_extension` | `CREATE EXTENSION btree_gist` (prerequisite for the GIST exclusions below) |
| `20260427143408_sa_effective_range_exclusion` | Generated `effective_range tsrange` column on `service_agreement` + `no_overlapping_active_sa` partial GIST exclusion + `chk_sa_end_ge_start` CHECK |
| `20260427143900_sam_effective_range_exclusion` | Same pattern on `service_agreement_meter` + `no_double_assigned_meter` exclusion + `chk_sam_removed_ge_added` CHECK |
| `20260427144400_sa_lifecycle_invariants` | `enforce_sa_lifecycle_invariants` BEFORE INSERT/UPDATE trigger on `service_agreement` |
| `20260427162359_point_in_time_helpers` | `responsible_account_at()` and `meter_assignment_at()` SQL functions |

**Pre-existing data:** the new constraints don't reject existing rows — they only block new violations. However, pre-existing orphaned `service_agreement_meter` rows (parent SA is FINAL/CLOSED but the SAM has `removed_date IS NULL`) will continue to exist until a separate cleanup is run. This is the bug `closeServiceAgreement` fixes prospectively, but historical orphans need a one-time `UPDATE service_agreement_meter SET removed_date = sa.end_date FROM service_agreement sa WHERE service_agreement_id = sa.id AND removed_date IS NULL AND sa.status IN ('FINAL', 'CLOSED')` script. **Tracked as a follow-up task; not in Slice 1.**

**`tsrange` vs. `tstzrange`:** Postgres requires generation expressions to be `IMMUTABLE`. `date::timestamptz` is `STABLE` (timezone-dependent), which Postgres rejects. `date::timestamp` (without time zone) IS immutable. Since `start_date`/`end_date` are `DATE` columns with no time-of-day semantics, `tsrange` is the correct type — calendar-date overlap, no timezone reasoning needed.
